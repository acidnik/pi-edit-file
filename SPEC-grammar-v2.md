# edit_file — расширение грамматики (spec, v2)

СТАТУС: РЕАЛИЗОВАНО (2026-09-30). В §3 утверждён вариант B (`NNN+ DELIM`);
§10 — фикс exact-run семантики делимитера. 88/88 тестов, реальные chain-патчи
сессии 2026-09-30 переигрываются: скелет → переотправка → применение.

Фидбек из сессий (редактирование Rust/TS/Svelte-проекта, 19 отказов `edit_file`):

| Отказ | Кол-во | Причина |
|---|---|---|
| `expected a hunk header` | 15 | патч начинается с контента, без `NNN @@@` / `@@@` |
| `unterminated hunk` | 3 | нет закрывающего `@@@` перед следующим блоком / в конце |
| `hunk header before closing delimiter` | 1 | то же семейство |

Разбор реальных патчей из сессии 2026-09-30 (3 многохунковых цепочки) показал: модель
пишет не «патч с забытым заголовком», а **связку replace-цепочкой** — осмысленный
grammar, просто не тот, что задокументирован:

```
old line(s)
@@@
new line(s)
@@@
old line(s)
@@@
new line(s)
```

Это несколько пар `before → after` без заголовков. Парсер уже почти готов его
есть: after-блок и сейчас закрывается по EOF и по заголовку следующего хунка.
Не хватает только implicit-старта.

---

## 1. Цепочная форма: детект + skeleton-ответ (без автоприменения)

### Решение

Chain-grammar как входной формат НЕ легализуем: модель всегда пишет номера
строк. Но контент-start патч больше не бросает тупую ошибку — парсер
**детектирует** цепочку, разбирает её и, если блоки локализуются в файле,
отвечает **готовым скелетом патча**: заголовки с вычисленными номерами строк,
без самих строк. Скелет в ответе выглядит так (нумерация — реальные строки
файла, вычисленные парсером; `@@@` — строка-делимитер):

```
patch rejected — this looks like the chain form ("old DELIM new DELIM old ...").
Here is the same edit with proper numbered headers — paste your blocks between them:

12 @@@          <- header: your first old block starts at line 12
<your before block: 1 line — the block at src 12-12>
@@@             <- closing delimiter
<your after block: 2 lines>
@@@
30 @@@          <- header: your second old block starts at line 30
<your before block: 3 lines — the block at src 30-32>
@@@
<your after block: 1 line>
@@@
```

### Алгоритм

1. Первый непустой патч-строкой строка — не заголовок → chain-детект.
2. Блоки = сплит по собственным делимитерам (blank-строки между блоками
   игнорируются, внутри блока — контент). Нечётный последний блок — это before
   без after: в скелете для него рисуется заголовок + пустой after с подсказкой
   (delete через делимитер-терминатор или append через `NNN @@@` + пустой before).
3. Каждый нечётный (before) блок ищется в файле — тем же каскадом, что резолвер
   (exact → trim → collapse). Исход в скелете:
   - **Уникальный матч** → заголовок `NNN @@@` с реальной строкой (для
     trim/collapse — с пометкой «matched with whitespace differences»).
   - **Не уникален** (матчится в N > 1 местах) → НИКАКОГО авто-выбора: выбрать
     одно из N одинаковых вхождений без сигнала — ровно та двусмысленность,
     которую резолвер отказывается решать сам (см. hintless-семантику). Вместо
     номера — строка вида:
     `<NOT UNIQUE: matches at lines 12, 47 — extend the before-block with surrounding lines to make it unique, then re-emit with the chosen NNN>`
     Кандидаты перечисляются все (при ≤5), при большем числе — первые 5 и
     «… and N more». Модель либо расширяет блок контекстом (предпочтительно),
     либо сознательно берёт нужный номер.
   - **Не найден** → `<NOT FOUND: this before-block does not appear in the file
     (exact, trimmed and whitespace-collapsed matching all failed)>` — вероятно,
     модель писала блок по памяти; перечитать файл.
4. Ответ = model-facing текст со скелетом; файл НЕ пишется. Если ВСЕ before-блоки
   локализованы однозначно — в скелете напротив каждого заголовка рисуется
   фактический диапазон строк исходного блока (`src 12-12`), чтобы модель могла
   сверить намерение с локацией до пере-отправки.

### Почему не авто-применение

Один лишний round-trip, но: (а) модель видит правильный формат на своём же
примере и переучивается; (б) нулевой риск молчаливой легализации неоднозначного
формата; (в) uniqueness-проверка всё равно требует резолва до применения.

## 2. Артефакты формата, которые прощаем

- **Хвостовые пустые строки в after-блоке, закрытом по EOF** — отбрасываются
  (артефакт финального `\n` в JSON-строке; в реальном патче после контента шли 2 пустые
  строки — сейчас они бы доехали до файла как пустые строки в конце).
  Пустые строки перед явным `@@@`-терминатором не трогаем (могут быть контентом).
- **`NNN@@@` без пробела** — HEADER_RE ослабляется с `^(\d+)\s+` до
  `^(\d+)(\+)?\s*` (см. §3). Строка контента `42@@@` теперь заголовок —
  осознанный tradeoff, таких строк в коде практически не бывает, а выгода —
  минус целый класс опечаток в заголовке.

## 3. `NNN+ DELIM` — явная форма insert-after (РЕШЕНО: вариант B)

Проблема (из фидбека): insert вставляет **перед** строкой NNN, модель ожидала
«после» — код оказался снаружи функции, словил линтер при следующей проверке типов. ВАЖНО: это НЕ
off-by-one в смысле толерантности матча — у insert нет before-блока, нечего
искать, ±20 не помогает. Направление — чистая семантика: оба варианта
легитимны, и фаззи-матчинг бессилен, т.к. ошибки в данных нет.

### Правило

- `NNN DELIM` + пустой before → вставить **перед** строкой NNN (как сейчас).
- `NNN+ DELIM` + пустой before → вставить **после** строки NNN.
- `NNN+ DELIM` с непустым before → ошибка: «+ suffix is only valid for inserts —
  a replace anchors the matched block itself».
- `0+` → ошибка `insert-after needs NNN >= 1`.
- `NNN+` = последняя строка файла → вставка в конец (та же логика
  «past the last line», что у обычного insert).

### Представление

HEADER_RE ослабляется до `^(\d+)(\+)?\s*([DELIM]{3,})\s*$` (попутно прощает
`NNN DELIM` без пробела — §2). `Hunk` получает `insertAfter?: boolean`.
Резолвер: для insert-хунка точка вставки = `hint` (before) или `hint + 1`
(after). `insertAfter` при `hint === null` — ошибка парсинга (bare-делимитер
не может быть вставкой — нечего матчить; правило формата не меняется).

### Отчёт

- `hunk 2: insert BEFORE src line 12 → out line 12 (0 → 3 lines)`
- `hunk 2: insert AFTER src line 12 → out line 13 (0 → 3 lines)`

## 4. No-op хунки

Хунк с `before`, эквивалентным `after` **exact**-сравнением, — мусор (модель
описалась в батче, фидбек п.4). Раньше это либо падало, либо применялось
вхолостую.

### Правило

- exact `before == after` (поэлементно, без trim) → хунк **пропускается**:
  не резолвится, не применяется, в отчёте строка `hunk N: no-op (before == after) — skipped`.
  Батч применяется, если остальные хунки валидны.
- trim-эквивалентный, но не exact → применяется как обычный replace
  (это осмысленная нормализация пробелов, её не маскируем).
- Все хунки батча no-op → ничего не пишется, отчёт `nothing to change (all hunks are no-ops)`.

Реализация: фильтр в extension-обёртке перед `resolveHunks` (ядро остаётся
чистым парсером/резолвером), номер хунка в отчёте — исходный (по порядку в патче).

## 5. Тексты ошибок (точные)

- **Chain-детект сработал** — не ошибка, а skeleton-ответ (§1). Текст начинается
  с `patch rejected —` (чтобы модель точно поняла, что ничего не записано) и
  содержит скелет + короткие правила формата.
- **Патч вообще без делимитера** (ни одного `@@@`, чистый search/replace):
  `parse error: no "@@@ " delimiter found — a replace patch needs the old block, a "@@@ " line, then the new block (see tool description)`
- **`NNN+` на replace** и **`0+`**: см. §3 (по выбору варианта).
- Сообщение `expected a hunk header` исчезает: content-start теперь всегда
  chain-детект. Ветка остаётся только для патча из одних пустых строк.

## 6. Изменения в отчётах

- Insert-хунки формулируются однозначно:
  - `hunk 2: insert BEFORE src line 12 → out line 12 (0 → 3 lines)`
  - `hunk 2: insert AFTER src line 12 → out line 13 (0 → 3 lines)` (если §3 = вариант B)
- No-op: `hunk 3: no-op (before == after) — skipped`.
- В конец model-facing текста добавляется строка-подсказка про устаревающие
  номера (фидбек п.3): `follow-up edits: use the out-numbers from this report as hints — they match the file as it is now`.

## 7. Description тулза (extension.ts)

К описанию добавляются: правило «inserts go BEFORE line NNN», форма
`NNN+ DELIM` для insert-after, no-op поведение. Пример в описании дополняется
insert-after на `NNN+`.

## 8. Что сознательно НЕ делаем

- **Bare-делимитер для вставки** — у вставки пустой before, нечего матчить для
  уникальности; явный `NNN+ DELIM` закрывает потребность.
- **Синтез suggested-corrected-hunk на parse-ошибках** — chain-патчи получают
  skeleton-ответ (§1), остальные parse-отказы исчезают или редки; механический
  синтез подсказки возможен только для пары случаев, выгода мала. Оставляем
  детальные тексты ошибок (§5).
- **Авто-применение chain-патчей** — только скелет для пере-отправки (§1).
- **Изменение семантики существующих форм** — ничего из того, что парсилось,
  не меняет значения.

## 9. План проверки

Юнит-тесты (test/core.test.ts):

1. Chain-детект: чётная цепочка `A DELIM B DELIM C DELIM D` → скелет с двумя
   парами заголовков (по образцу реальной цепочки импортов), файл не изменён.
2. Chain-детект: блок не уникален → в скелете `<NOT UNIQUE: matches at lines …>`
   со ВСЕМИ кандидатами (≤5), без авто-выбора; расширение блока контекстом даёт
   уникальный номер при пере-отправке.
3. Chain-детект: блок не найден → `<NOT FOUND …>`; trim-уникальный блок → номер
   с пометкой «matched with whitespace differences».
3. Chain-детект: нечётный хвост → скелет с подсказкой про delete/append.
4. Один блок без единого делимитера → ошибка «no delimiter found».
5. Хвостовые пустые строки при EOF-закрытии after — отброшены (явные патчи).
6. `NNN@DELIM` без пробела — заголовок (ослабленный HEADER_RE).
7. `NNN+ DELIM`: в середину, после последней строки; на replace → ошибка; `0+` → ошибка.
8. No-op exact — скип с отчётом; trim-но-не-exact — применяется; все no-op → «nothing to change».
9. Регресс: все существующие тесты проходят без правок (кроме обновлённых в b0ef0b7).

Ручная проверка: переиграть три реальных chain-патча из сессии 2026-09-30 —
каждый должен вернуть корректный скелет с первого раза, а повторный вызов
со скелетом — примениться.

## 10. Попутно найденный баг: длина делимитера и «escalate to a longer run»

Description советует: «if the file content contains a line like @@@, escalate
to a longer run (####)». Это НЕ работает:

- `isOwnDelim` проверяет `delimiterChar(line) === delimChar`, а DELIM_RE матчит
  3+ повторов — строка `###` считается делимитером даже при `####`-делимитере,
  т.е. «эскалация» не спасает контент с `###`.
- Хуже: контент-строка `@@@` при `####`-делимитере бросает «delimiter collision —
  keep one delimiter character» — то есть строку-делимитер как контент нельзя
  записать НИКАКИМ делимитером. Именно поэтому эта спека правилась питоном.

Фикс (в эту же волну изменений): делимитер = **точная полная строка-повтор**,
используемая в заголовке этого вызова (`"####" === line`), а не «3+ того же
символа»; строки-повторы той же длины, но другого символа, и более короткие
повторы — легальный контент. Тест: правка файла, содержащего строку `@@@`,
делимитером `####`.

## 11. Фидбек 2026-10-01: обучаемость грамматики и устаревшие якоря

Фидбек из другой сессии (≈15 вызовов edit_file, 4 отбоя). Разбор показал: две из
четырёх «проблем» — не отсутствие возможностей, а их невидимость (bare-form и
`NNN+` были реализованы и покрыты тестами, но жили в буллетах описания), одна —
реальный пробел в диагностике, одна — реальный пробел в отчёте.

Что изменено:

- **Description ведёт тремя формами** — anchored replace, bare-replace (без NNN,
  блок уникален) и insert (`NNN @@@` / `NNN+ @@@`) с примером на каждую.
  Раньше шапка учила только нумерованному replace.
- **Преамбула скелета** (`chainSkeleton`) больше не читается как «нумерация
  обязательна всегда»: сказано, что chain-форма нелегальна, а одиночный
  уникальный блок может начинаться с голого делимитера.
- **Скелет на все grammar-отказы, где он структурно корректен**: добавлены коды
  `missing-separator` (заголовок там, где должен быть закрывающий делимитер) и
  `unterminated` (нет закрывающего делимитера). Unified-diff и
  delimiter-mismatch оставлены со своими точечными подсказками: два
  конкурирующих примера в одном ответе путают сильнее, чем помогают.
- **`reportCaveats`** — предупреждения идут ВЫШЕ построчных отчётов: смещённый
  якорь (`anchor 20 was off by 49` + реальный `src`-диапазон, а за пределами ±20
  ещё и «verify it is the right block») и, для мульти-хунка, напоминание, что все
  хунки вызова матчатся по ОРИГИНАЛУ, а out-номера — для следующего вызова.
  Прямой ответ на кейс «второй хунк пронумерован по результату первого».
- **`insertTip`** — если replace сохраняет старый блок и только добавляет строки,
  в конце отчёта появляется короткая форма (`NNN+ @@@`), с делимитером этого же
  вызова (`patchDelimiter`).
- **`patchDelimiter(patch)`** — вынесен из `chainSkeleton` и стал публичным.
- **UI показывает только дифф**: построчные report-строки, caveats и `insertTip`
  больше не рисуются в транскрипте (запрос Ника 2026-10-01: «только сам дифф») —
  они остаются в model-facing `content` и в `details.reportLines` для экспорта и
  отладки.

Ограничение, найденное при правке самого описания (продолжение §10):
**`edit_file` не может записать контент, содержащий строки-заголовки** вида
`NNN DELIM`. Внутри after-блока такая строка обрывает блок
(`parseHunkHeader(...).hint !== null`), и внешний цикл читает её как следующий
хунк: при том же делимитере получается мусорный хунк, при другом — жёсткий
`delimiter mismatch`. Поэтому `DESCRIPTION` (в нём примеры с `42 @@@` и
`120+ @@@`) правился не тулом, а точечной заменой через python. Варианты фикса,
если понадобится: (а) эскейп-маркер для строки-заголовка внутри блока;
(б) распознавать заголовок только после терминатора — но это ломает поддержку
пропуска терминатора между хунками.

## 12. Одно-делимитерный патч без заголовка (баг-репорт 2026-10-02)

Симптом: патч «content / DELIM / content» (ведущий `@@@` забыт) отклонялся как
chain-form с текстом «with two or more blocks every block needs its own header»,
хотя строка-делимитер ровно одна, хунк ровно один, и chain-form там невозможен по
определению. Тот же патч с ведущим `@@@` проходил.

Причина: `parsePatch` бросал `content-start` на первой же не-заголовочной строке,
а текст сообщения собирался в `chainSkeleton` без всякого подсчёта блоков.

Фикс:

- `headerlessSingleHunk(patch)` — если в патче НЕТ строк-заголовков и ровно одна
  строка-делимитер, он читается как один hintless-хунк: `before`/`after` по краям
  делимитера, краевые пустые строки срезаются, уникальность before проверяет
  обычный резолвер (неоднозначный блок по-прежнему отклоняется, авто-выбора нет).
  `Hunk.leadingDelimiterOmitted` помечает такой хунк, и `reportCaveats` добавляет
  model-facing nudge «напиши заголовок явно» — каноническая форма остаётся
  единственной, которую учит описание.
- Отказ остаётся для действительно неоднозначных случаев: ≥2 делимитеров без
  заголовков и/или любая нумерованная строка-заголовок где-то в патче (там
  работает прежний скелет).
- Текст отказа исправлен — больше не утверждает число блоков, которого не знает:
  «the patch opens with content instead of a hunk header, and the chain form … is
  not legal input — every block needs its own header», и рядом по-прежнему
  подсказка про голый делимитер для одиночного уникального блока.

## 13. Строгая уникальность, явный вердикт, no-op как ошибка (фидбек 2026-10-02)

Фидбек: «что бы меня удержало на edit_file» — (1) явное различие между
«применено и уникально» и «якорь не найден / не уникален», причём второе как
ошибка, а не строка в отчёте; (2) отказ принимать патч, где before == after,
держать громким; (3) `LOW CONFIDENCE: matched outside the ±20 line window`
переформулировать как «применено, якорь уникален, номер строки не совпал с
подсказкой» — в прежней формулировке это читалось как предупреждение об
опасности и уводило в другой инструмент.

Решения (подтверждены Ником): уникальность — строгая; no-op-отказ — только
когда no-op'ов весь патч.

- **Строгая уникальность.** Резолвер требовал уникальности только при
  отсутствии подсказки и при равенстве расстояний; в остальных случаях
  выбиралась копия, ближайшая к NNN, а в отчёте появлялась строка
  `[also matches at lines … — verify the right one]`. Теперь любое число
  кандидатов > 1 — отказ: `not unique — the before-block matches at lines …, (tier
  match, N copies)` + совет расширить блок контекстом («a line number cannot
  choose between identical blocks»). `findCandidates` сканирует файл целиком на
  каждом тире: копия за пределами окна ±20 больше не «невидима». Из `MatchInfo`
  удалён `otherMatches`, из отчёта — обе прежние скобки (`also matches` и
  `LOW CONFIDENCE`). NNN остался только мерой «насколько номер разошёлся с
  реальностью» (`farFromHint` сохранён как данные, но не рисуется как
  предупреждение).
- **Явный вердикт первой строкой.** Успех: `applied — N of M hunk(s), file
  written` (`appliedLine()`), отказ: `batch rejected — 0 of M hunk(s) applied,
  nothing was written to the file`. Строка-вердикт идёт ВЫШЕ caveats, чтобы
  «применено» и «отклонено» нельзя было спутать, читая построчные строки.
- **no-op.** В смешанном батче хунк остаётся пропущенным, но с громкой пометкой
  `SKIPPED — no-op (the old block equals the new block); this hunk changes
  nothing`; патч, целиком состоящий из no-op'ов, теперь **ошибка**:
  `nothing applied — every hunk of this patch is a no-op …, so the file was NOT
  written` (раньше это был успешный ответ «nothing to change», который прятал
  сигнал «не те строки скопированы»). Проверка и фильтрация no-op'ов живут в
  `extension.ts` (там же, где были), `isNoOpHunk()` — в ядре.
- **Caveats читаются как факт**: `note: hunk 1's hint 20 was off by 49 — the
  block was found by content and is unique, so the edit was applied at src
  69-72.` Прилагательное «дальний якорь» больше не подаётся как риск: блок
  уникален, а значит применён там, где он есть.
